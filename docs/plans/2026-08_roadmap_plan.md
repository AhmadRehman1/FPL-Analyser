## Track A — Priority 10 Field Simulator (Phases B/C/D)

### Approach

The design doc's own unresolved questions (`docs/priority10_field_simulator_design.md:111-129` — sampling size, rate-limit/caching discipline, data-handling scope, performance budget) are about scaling *beyond* the shipped n=200 baseline, so scaling up must re-validate them, not skip them.

Then Phase B (joint simulation core), Phase C (rank-distribution diagnostic, opt-in/diagnostic-only), Phase D (backtest validation, current-season-only — real historical rival snapshots predating Phase A's ingestion start are unrecoverable, already disclosed in the design doc).

### Key Decisions

- **[A1] Sampling scale: 2,000 entries from the Overall league** (10x the current 200), Overall-league-only (no additional mini-leagues — none was named). *Basis:* [assumed: 2,000 as a round order-of-magnitude increase — if wrong: the A-1 build phase measures real timing/error-rate at this scale first, so the number is easy to revise before Phase B depends on it]. Blast radius if wrong: re-run A-1 at a different N; nothing downstream breaks because Phase B reads whatever sample size exists.
- **[A9] Retention policy: `fact_rival_squad_sample` retains only the current season's rows.** A scheduled purge removes rows from any prior season. *Basis:* Phase D (backtest validation) is already scoped to the current live season only (verified: `docs/priority10_field_simulator_design.md:103-109`) — no downstream use case in this plan ever reads a prior season's rival-squad sample, so nothing is lost by not keeping it. This is the actual engineering control for the landmine named in Risks & Landmines below ("increased real personal data retention at scale") — rate-limiting (A-1) and excluding mini-leagues bound *load* and *breadth*, but only this purge bounds the *volume of real people's picks retained over time* as sampling scales 10x. Without it, "scale up sampling" plus "keep running this indefinitely" means unbounded accumulation of real managers' squad choices, which the no-names design in `fact_rival_squad_sample` (schema `0017_priority10_phaseA_rival_squad_sample.sql`) reduces the sensitivity of but does not itself bound the volume of.
- Phase C remains diagnostic-only, never wired into `squad_optimizer`'s search (verified: `docs/priority10_field_simulator_design.md:93-102` — matches the existing, already-shipped pattern of `monte_carlo.run()` never influencing the MIQP search).
- Phase D is scoped to the current live season only (verified: `docs/priority10_field_simulator_design.md:103-109`).

### Data Changes

No existing table is altered. A season-scoped purge (per [A9]) deletes rows rather than adding a table.

## Track B — Recalibration Cadence + Automated Promotion

### Approach

Move from "recalibration runs weekly, a human manually confirms via `review_recalibration.py`" to "recalibration runs weekly and promotes itself when safe." This requires two things the roadmap item's one-line description doesn't mention but which recon surfaced as necessary: (1) a single source of truth for "the active parameter version," replacing the hardcoded literals in `run_ingestion.py` and `export_track_record.py`, since automated promotion has nothing to update otherwise; (2) a compensating safety control in place of the human reviewer, since versions the auto-promoted parameters are immutable but *live* — a bad promotion would silently degrade real user-facing recommendations with nobody watching.

**Scope correction (found starting Phase B-1, before any code was written — see [A12]):** Phase B-1 as originally written named exactly two files (`run_ingestion.py`, `export_track_record.py`) needing to read the active version instead of a hardcoded literal. Grepping every version-argument name `recalibrate()` can actually produce a new version for (`xi_params_version`, `rho_params_version`, `rho_residual_params_version`, the four minutes-model version args, `lambda_params_version`, `kappa_tc_params_version`) shows this was a significant undercount: `rho_residual_params_version`, `lambda_params_version`, and `kappa_tc_params_version` alone each appear as hardcoded call-site arguments across roughly a dozen files in `scripts/` (`explain_my_move.py`, `export_leaderboard.py`, `export_projections.py`, `grade_squad.py`, `print_chip_timing_roadmap.py`, `run_backtest.py`, `run_ingestion.py`, `run_report.py`, `run_scenarios.py`, `run_season_simulation.py`, `run_transfer_planner.py`, `run_transfer_planner_for_real_squad.py`, `track_elite.py`) — effectively every real-data script in this project, several of which run back-to-back in the same `scheduled_pipeline.yml` job and must all resolve the *same* active version consistently, or different sections of the same report would silently disagree. This is not a "single source of truth, two call sites" change; it's a project-wide plumbing change touching the majority of `scripts/`. See [A12] and the revised Phase B-1 below — **this was flagged to the human before further code was written, per this plan's own danger-rule discipline for a change this size on the single highest-blast-radius track in the plan.**

**Architectural correction (found building Phase C-1, before Track B was built — see [A10]):** `db/fpl_quant_v2.duckdb` is gitignored and does not survive between separate GitHub Actions jobs on its own. Confirmed directly: `scheduled_pipeline.yml` (the twice-daily workflow that actually runs `run_ingestion.py` and most other real-data scripts) has an `actions/cache/save@v6` step for that path but **no matching restore step**, so every one of its own runs starts from a freshly-seeded DB; `weekly_backtest.yml` (where Phase B-3 wires in promotion) only *restores* that cache, and never saves it back. A promotion written only to a DB table during `weekly_backtest.yml`'s Sunday run would therefore be invisible to every `scheduled_pipeline.yml` run afterward — the exact pipeline generating every real recommendation would silently revert to the original hardcoded defaults within hours, defeating Phase B entirely without any error or warning. **As built, there is no separate DB table or new file format at all** — see [A3]/[A10]'s revised text below for what was actually simpler to build.

### Key Decisions

- **Automate confirm too, not just the run** (user, overriding my recommendation). This is the plan's single highest-blast-radius decision: it removes a deliberate, already-shipped human review gate (`review_recalibration.py`, only `status=='confirmed'` rows are ever auto-loaded, verified: `backtest.py:1405-1467`) from a path that drives what real users see. It is followed through here, not patched with one line — see [A2]/[A3]/[A10] and the compensating controls below, and Risks & Landmines.
- **[A2] Regression check — revised from a "2% threshold on log_score_/brier_ metrics" to what's actually cheap to compute (found while building Phase B-2, before it was marked done).** The originally-imagined check would need a *second* full walk-forward backtest per pending proposal to see whether adopting it regresses the standard `backtest_metrics` (log_score_*/brier_*) — but each `scripts/run_backtest.py` run is a real ~1-2 hour job (its own module docstring), so that's not affordable per proposal in an automated cadence. What's actually cheap: every family except `rho_residual` only ever gets a proposal when its own refit already found a strict improvement in its own optimized metric (`refit_xi_rho()` etc. all guard with `if result[...] != current[...]`) — so there is no in-space "regression" to catch by construction; the real risk there is a numerically-noisy near-tie, not a regression. `rho_residual` is a moment-matched value (not a scored search — see `refit_rho_residual()`'s own call site, which has no such guard), so "improvement" doesn't apply to it at all. `evaluate_and_promote_proposal()` (`src/fpl_quant/backtest.py`) implements this honestly: a per-`metric_name` direction table (`_METRIC_DIRECTION`) checks the refit's own before/after value moved the right way and by more than a noise floor (`min_relative_improvement`, default 0, i.e. any real improvement — an operator can raise it once real proposal history exists to show what noise looks like); `rho_residual` (`_NOT_A_SCORE_METRICS`) promotes whenever the value actually changed. **Disclosed residual risk, not further mitigated here:** a proposal that improves its own target metric could still regress some other, unrelated standard metric — named in Open Items, not assumed away.
- **[A3] Active-version source of truth: no new file or DB table at all.** `backtest.active_recalibratable_versions(seed_dir)` resolves the active version per (family, key) directly from the **existing** `data/recalibration/seeds_*.json` files (via `resolve_active_version()`, which takes the highest `new_params_version` among *confirmed* seeds for that family/key, falling back to the original default) every time it's called — simpler than building a second, parallel "active version" artifact that could itself drift out of sync with the seed files. `RECALIBRATABLE_VERSION_ARGS` is the one place the 8 version-argument-name → (family, key) mappings live; every script calls this once and reads the dict, rather than each re-deriving it.
- **[A10] The committed seed files are the only source of truth — there is no DB table to keep in sync with them.** See the Approach note above for why a DB-table-only design would have silently done nothing. A promotion (Phase B-2) writes straight to the same `data/recalibration/seeds_*.json` files `write_recalibration_seed_file()` already produces, via the exact mechanism `review_recalibration.py --confirm` already uses — so `weekly_backtest.yml`'s existing commit step (which already commits `data/recalibration/`) picks up every promotion with no separate wiring.
- Reversibility: because `params.py`'s versions are immutable and append-only (verified: `params.py:28-119`), and because `active_recalibratable_versions()` only ever counts *confirmed* seeds, "rollback" is just flipping a proposal's status away from `confirmed` — `review_recalibration.py --reject` (already existing, unchanged) does exactly this, whether the proposal was confirmed by a human or auto-promoted. No new rollback command was needed — see Phase B-3.
- `review_recalibration.py`'s manual `--confirm`/`--reject` stays usable as an override/audit tool even though it's no longer the only path to promotion; a new `--list-confirmed` flag shows every confirmed proposal (human or auto) with who/when, since discovering what's eligible for `--reject` matters once promotion is automated.

### Data Changes

None beyond what Track C's persistence lesson already implied: no new schema, no new DB table, no new committed-file format. `recalibration_proposals.status='confirmed'` (already existing, verified: `schema/0008_m7_backtest.sql:61-77`) is reused for auto-promotions too — distinguished from a human confirmation via `reviewed_by='auto-regression-gate'`, not a new status enum value (avoids a DuckDB CHECK-constraint migration entirely, and needs zero changes to `load_confirmed_recalibration_seeds()` or anything that already reads `status='confirmed'`).

### Edge Cases

- A proposal whose own refit metric is a near-tie with the current value → held pending (`min_relative_improvement` noise floor), not silently promoted on a coin-flip.
- `rho_residual`'s refit has no `if new != current` guard, so a proposal can represent no real change at all → held pending rather than promoted as a no-op.
- Two pending proposals for the same `(family, key)` → each evaluated independently by proposal_id; `resolve_active_version()` takes the max confirmed version, so whichever is confirmed with the higher `new_params_version` wins regardless of evaluation order.

### Requirements

- **R5**: WHEN any script needs the active version for a recalibratable parameter family/key THE SYSTEM SHALL resolve it from the git-committed confirmed-seed files (`backtest.active_recalibratable_versions()`), not a hardcoded literal.
- **R6**: WHEN a recalibration proposal's own refit metric has genuinely improved beyond the noise floor (or, for `rho_residual`, genuinely changed) THE SYSTEM SHALL auto-promote it and log the decision; WHEN not, THE SYSTEM SHALL leave it `pending` with a logged reason.
- **R7**: WHEN an operator needs to undo an auto-promotion THE SYSTEM SHALL support reverting it via a documented command.

  **The blind critique pass found one CRITICAL bug in this initial design, fixed before this phase was marked done:** `adjustment_params_version` (`minutes_adjustment_params`'s shared `magnitude`/`cap` version-argument) was originally resolved as "any key confirmed, take the max version" — but `propose_recalibration()` assigns each `(family, key)` proposal its own next-available version via `_next_param_version()`, which is scoped to the family, not the family+key, so `magnitude` and `cap` proposed together (as `recalibrate()`'s `MINUTES_PARAM_GRIDS` loop always does) land on two *different* version numbers. "Any key, take the max" would therefore often resolve to a version where only one of the two keys has a row at all, and `resolve_param()`'s hard-error (no-fallback) lookup would crash the entire real-data pipeline the first time this family was ever confirmed.
